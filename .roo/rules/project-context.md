# KPPDF 2.0 — Контекст проекта

## Что это?

**KPPDF 2.0** — PLM + ERP + CRM платформа для малого производства. Центральная концепция — **Цифровой Двойник (Digital Twin)** изделия, проходящий полный жизненный цикл от заказа до паспорта эксплуатации.

## Триединство систем

- **CRM** — слой требований клиента (`IRequirement`): что заказано
- **PLM** — слой инженерного проектирования (`BOM` + `IAttributeValue`): как спроектировано
- **ERP** — слой ресурсов и производства (`MaterialItem` + `Order` + `WorkTask`): как произведено

## Жизненный цикл изделия

```
Ordered (Заказано) → Designed (Спроектировано) → Built (Произведено) → Maintained (Паспорт/Эксплуатация)
```

## Предметная область

- **Цифровые двойники (Digital Twins)** — изделия с полной спецификацией: EAV-атрибуты, BOM-дерево, чертежи
- **Заказы (Orders)** — клиентские требования, привязанные к эталонным изделиям
- **Товары / Материалы (Products / Materials)** — номенклатура, цены, складские остатки
- **Клиенты (Clients)** — контрагенты: юрлица и физлица
- **Пользователи (Users)** — сотрудники (менеджеры, инженеры, производственники)
- **Документы (Documents)** — КП, счета, паспорта изделий (PDF)
- **Шаблоны (Templates)** — визуальное оформление PDF, категорийные шаблоны атрибутов
- **Производство (Production)** — наряды, техпроцессы, Гант-графики

## Технический стек

- **Angular 21+** — Standalone components, Signals, inject().
- **SCSS + BEM** — стилизация.
- **PrimeNG 21+** — Aura, PrimeIcons.
- **RxJS** — только HTTP и внешние потоки.
- **Backend** — в обсуждении (Express + MongoDB / NestJS + PostgreSQL).
- **PDF-генератор** — jsPDF / Puppeteer.

## Ключевые сценарии

1. Создание Цифрового Двойника изделия (категория → шаблон атрибутов → BOM)
2. Коммерческое предложение на основе эталонного изделия
3. Проверка соответствия (Compliance) спроектированного — заказанному
4. Расчёт себестоимости и планирование закупок по BOM
5. Производство + Гант + Госприёмка
6. Генерация паспорта изделия (as-maintained PDF)
7. Отправка клиенту (email/ссылка)

## Архитектурные решения (зафиксированные)

- Микро-архитектура: `core/`, `shared/`, `entities/`, `features/`, `pages/`.
- NGRX не используется. Всё состояние — на Signals.
- Строгая типизация, `any` запрещён.
- Компоненты — только Standalone, OnPush, SCSS BEM.
- DI — только через `inject()`.
- Spec: `.roo/rules/plm-spec.md` — мастер-план трансформации.

## Критические замечания

- **Не менять архитектуру без подтверждения.** Любые изменения слоёв, добавление новых библиотек состояния или глобальных паттернов — только после обсуждения.
- **Digital Twin — ключевая фича.** Вся архитектура строится вокруг EAV-ядра и BOM-дерева.
- **Compliance — конкурентное преимущество.** Автоматическая проверка «заказано vs спроектировано vs произведено».
- **Производительность важна** — BOM может содержать 100+ узлов, расчёт себестоимости — рекурсивный.
