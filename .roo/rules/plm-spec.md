# PLM-Spec: Мастер-план архитектурной трансформации

Этот документ — техническое задание (Spec) для реализации PLM + ERP + CRM ядра KPPDF 2.0.
Все агенты обязаны сверяться с этим Spec при проектировании новых сущностей и фич.

## 1. Концепция и Видение

**Смена парадигмы:** Переход от хранения «описания текстом» к модели **«Цифрового Двойника»** (Digital Twin) изделия.

**Триединство систем:**
- **CRM** — Слой требований клиента (`IRequirement`)
- **PLM** — Слой инженерного проектирования (`BOM` + `DesignValue`)
- **ERP** — Слой ресурсов, производства и отгрузки (`MaterialItem` + `BuiltValue`)

**Жизненный цикл данных:**
```
Ordered (Заказано) → Designed (Спроектировано) → Built (Произведено) → Maintained (Паспорт/Эксплуатация)
```

## 2. Структура данных (Core Types)

### EAV-ядро (Универсальность)
- `IAttributeDef` — метаданные атрибута (тип, единица измерения, оператор сравнения)
- Типизированные значения: `number`, `dimension` (80х80х3), `enum` (RAL, сорта), `boolean`, `range`
- Динамические группы атрибутов (Геометрия, Электрика, Покрытие)

### Иерархический BOM (Дерево состава)
- Переход от плоского списка к древовидной структуре `IComponentNode.children[]`
- Типизация узлов: Сборка, Деталь, Закупной товар, Техпроцесс
- Связь узла с чертежом (`drawingRef`) и версией (`version`)

### Гибридная модель материалов
- `material: string` — для быстрого ввода
- `materialId: GUID` — для связи с каталогом ТМЦ и расчёта себестоимости

## 3. Бизнес-логика (Business Rules)

- **Шаблоны категорий:** каждой категории (Скамья, Павильон, Стелла) — свой набор обязательных атрибутов и типовой BOM
- **Compliance:** автоматическое сравнение реальных параметров (`IAttributeValue`) с требованиями CRM (`IRequirement`)
- **Процессный слой:** привязка атрибутов к операциям (атрибут "Площадь покраски" → операция "Порошковая покраска" с расходом материалов)

## 4. Команда Агентов

| Агент | Роль |
|---|---|
| `@meta-architect` | EAV-ядро, BOM-дерево, категории, DynamicAttrForm |
| `@production-planner` | BOM → склад, закупки, расчёт сроков/себестоимости |
| `@compliance-validator` | Проверка изделия на соответствие ТЗ клиента и ГОСТ |

## 5. Технический стек (целевой)

- **Shared Types:** единый источник правды для Frontend и Backend
- **Backend:** (обсуждается — NestJS + PostgreSQL с JSONB vs Express + MongoDB)
- **Frontend:** Angular + PrimeNG → DynamicAttrForm, BOMTreeEditor, PassportGenerator

## 6. Ключевые компоненты Frontend

- **DynamicAttrForm** — автоматическая генерация полей ввода на основе `valueType` (p-inputNumber, p-select, p-inputText)
- **BOMTreeEditor** — визуальный редактор структуры изделия (p-tree с drag&drop)
- **PassportGenerator** — сборка данных в PDF на основе финального состояния `as_maintained`

## 7. Action Plan (очередность)

1. **Backend:** Подготовить миграции БД под новую структуру (Categories, AttributeDefs, AttributeValues, ComponentNodes)
2. **Frontend:** Создать сервис-маппер, который превращает сырые данные БД в дерево для p-tree
3. **Системный аналитик:** Заполнить «Справочник материалов» и «Шаблоны категорий» на основе примеров изделий
